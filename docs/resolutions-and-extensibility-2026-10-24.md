# 対応解像度と拡張しやすさの検討

確認日: 2026-10-24。対象は `claude/tauri-ui`（`2.0.0-beta.1` 以降）。

## 対応する解像度を増やす必要はない

カードの位置は、解像度ごとの一覧ではなく、画像の高さから計算している（`predict_card_box`: 高さ1440を基準に、カードの幅894・高さ1302・上端69を比例させ、横は中央に置く）。16:9 の画面なら、1280x720・1366x768・1440x810・1600x900・2048x1152 も同じ式で扱える。位置がずれた場合は、画像から枠を検出して補正する処理が働く。つまり解像度を「足す」コードはなく、足しても処理は増えない。

### 実測

手元の2560x1440のスクリーンショット256枚を、`LANCZOS` で各解像度に縮小した画像を作り、解像度の指定なしで処理した（コマンドライン版、`--dry-run`）。

| 解像度 | 確定 | 元画像と同じカードID | 枠を推定した画像 | 時間 |
| --- | --- | --- | --- | --- |
| 2560x1440（元画像） | 256 | - | - | 1.4秒 |
| 1280x720 | 256 | 256 | 0 | 0.8秒 |
| 1366x768 | 256 | 256 | 0 | 0.9秒 |
| 1440x810 | 256 | 256 | 0 | 1.0秒 |
| 1600x900 | 256 | 256 | 0 | 1.0秒 |
| 2048x1152 | 256 | 256 | 0 | 1.5秒 |

結果は、すべて確定し、カードIDも元画像と一致した。小さい画像のほうが速いのは、画像の読み込みと縮小が軽くなるため。

### 限界

- これは、実際に各解像度で撮影した画像ではなく、2560x1440からの縮小画像である。ゲーム自身の描画（UIの拡大率、アンチエイリアス、ウィンドウ表示の枠）は再現していない。実機の撮影画像で確認するまで、「対応済み」とは書かない。
- 16:9 以外（ウルトラワイド、ウィンドウ表示）は、位置の検出と補正に頼る。これは今回の測定の対象外。
- 1366x768 は厳密には16:9ではない（1.7786）が、結果に影響しなかった。

## 結論（解像度）

追加の実装は不要。解像度の選択欄を戻す必要もない。README は「16:9の標準的な大きさに合わせて自動で位置を見つける」という説明にとどめ、実機での確認が済んだ解像度だけを具体的に書く。実機の画像が手に入ったら、同じ手順（元の画像と同じカードIDになるか）で確認する。

## 今後の機能追加のしやすさ

### 構成

| 層 | 場所 | 役割 | 大きさ |
| --- | --- | --- | --- |
| 判定・画像処理 | `rust/crates/mdript-core` | ハッシュ、枠の検出、照合 | 約1,100行 |
| 処理・保存・更新 | `rust/crates/mdript-cli` | 並列処理、保存名の予約、CSV、公式DB取得、登録 | `process.rs` 約1,430行（うちテスト約470行） |
| 画面とのつなぎ | `gui/src-tauri/src/lib.rs`、`migrate.rs` | コマンド、終了待ち、移行 | 約750行（うちテスト約200行） |
| 画面 | `gui/src/App.vue` | すべての画面と状態 | 約1,260行（script 565・template 194・style 499） |

### 機能別の見立て

| 追加したいもの | 変更が要る場所 | 難しさ |
| --- | --- | --- |
| 処理に関する新しい設定（例: WebP品質、英語版を保存しない） | 型、設定の保存対象、画面の入力、画面から処理への引数、`Options`、READMEの6か所前後 | 作業は単純だが、同じ項目が層ごとに別の名前で何度も出る（例: `skip_duplicate`／`duplicates`） |
| 英語版の画像を処理から外す | `prepare()` の1か所と `Options`、設定の経路 | 小さい。判定の流れは `prepare` と保存（`Sequencer`）に分かれていて、差し込みやすい |
| 保存名や出力先の規則の変更 | `Saver::reserve` と `safe_filename` | 小さい。ただし並列保存の予約と重複判定が絡むので、既存の並列テストを必ず通す |
| 新しいコマンド（例: 結果の再保存、フォルダ監視） | `lib.rs` に関数と登録、`types.ts`、`App.vue` | 中。終了待ち（`Busy`）に参加させる必要がある |
| 画面の大きな追加（設定画面、履歴、複数の出力先） | `App.vue` | 大きい。全部が1つのコンポーネントにあるので、追加するたびに読む量と衝突が増える |
| 新しい解像度・カードの種類 | 不要（上記）。新しいデータは `card_hashes.json` の更新 | 小さい |

### 強み

- 判定（core）と保存・更新（cli）と画面が分かれており、画面なしで処理を試せる（コマンドライン版）。
- Rust側のテストが厚い（合計62件）。並列処理の順序・panic・書き込み失敗・保存名の予約・CSV・移行・終了待ちを、テストで固定している。
- 判定の結果は旧Pythonとの比較用データで確認できる（256枚）。

### 弱み

1. **設定項目の配線が手作業で、層ごとに名前が違う。** 設定を1つ足すたびに複数のファイルを直し、直し忘れはコンパイルでは見つからない（例: 設定の保存対象のリストに足し忘れると、保存されないだけで、エラーにならない）。
2. **`App.vue` が1つに集まっている。** 状態（設定・結果一覧・確認パネル・登録・更新・終了）がすべて1つのスクリプトにある。次に画面の機能を足すなら、設定、結果一覧、確認パネルを別のファイル（composable）に分けてから足したほうが安全。
3. **画面の自動テストがない。** 今回の画面の確認（登録、閉じる、ログ失敗、移行）は、WebView2のリモートデバッグでアプリを操作する使い捨てのスクリプトで行った。リポジトリには入っていない。画面の変更で壊れても、CIは検出しない（型検査とビルドのみ）。
4. **`process.rs` が大きい。** 設定、引数の解析、判定、保存、並列処理、CSVの呼び出しが同居している。壊れやすい箇所（保存名の予約と並列の順序）は、テストで守られているが、読む量は多い。

## 提案（優先順）

1. 実機の撮影画像（1280x720〜4K）で確認する。足りなければ、解像度の対応は現状のまま。
2. 今回の画面確認のスクリプトを `tools/e2e/` に入れ、手動で再実行できるようにする（CIには入れない。実アプリが必要なため）。画面の機能を足す前に、これを足場にする。
3. 設定を1つ足す前に、設定項目の定義を1か所にまとめる（名前・型・既定値・画面の表示を1つの表から作る）。足し忘れをなくす。
4. 画面の機能を足す前に、`App.vue` を設定・結果一覧・確認パネルに分ける。

3と4は、機能を足す予定が決まってからでよい。予定がないうちにやると、使われない構造を作る。
