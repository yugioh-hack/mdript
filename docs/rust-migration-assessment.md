# Rust / Web UI 移行評価

2026-10-21。対象: ローカル commit `01e7121`、origin は https://github.com/yugioh-hack/mdript.git。
公開リポジトリと Releases は今回のWeb取得では失敗したため、公開最新版との一致・配布exeの容量は未確認。

## 判断

本資料は調査・試作方針の記録であり、Rustへの移行決定ではない。

Rust移行は検討に値するが、「全体1.8倍」を前提とした全面移植は推奨しない。
速度だけが目的なら現行版の実画像プロファイルと配布方式改善を先に行う。
UIも刷新するなら、Rust処理コア + TauriのWeb UIが有力。
ブラウザー単体版は配布不要という別の価値があるが、現行のフォルダ保存・公式DB更新をそのまま移すには制約が大きい。

## コードから確認したこと

- `phash.py`: Pillowのグレースケール変換とLanczos縮小、NumPyの32×32 DCT。純Pythonで画素を順番に処理しているわけではない。
- `catalog.py`: NumPyのXOR/popcount/partitionによる照合。NumPy 2系はbitwise_count。同順位の順序、同名カードの集約、中央領域での特別判定を持つ。
- `pipeline.py`: 最大8スレッド。WebPはquality=90、method=4、PNGはcompress_level=6。保存順、重複、予約・失敗時清掃も実装済み。
- `layout.py`: 通常枠で確定しない場合は検出・位置の探索を行う。この経路は通常確定と分けて計測が必要。
- `mdript.spec`: PyInstaller onefile構成。Python・NumPy・Tkを外せれば容量削減の余地はある。
- 同梱ハッシュJSONは665,449 bytes。READMEのexe約31MB、約0.05秒/枚は既存の説明値で、今回の実測ではない。

## 1.8倍という主張の感度分析

全体速度倍率 = 1 / ((1 - p) + p / s)。pは改善対象の時間割合、sはその部分の倍率。
下表は実測予測ではなく、仮定を変えたシミュレーション。
1,000枚50秒というREADMEからの換算値を参考スケールとして使用する。

| 改善対象p | 対象部分s | 全体倍率 | 1,000枚の換算 |
|---|---:|---:|---:|
| 20% | 1.8倍 | 1.10倍 | 45.6秒 |
| 50% | 1.8倍 | 1.29倍 | 38.9秒 |
| 80% | 1.8倍 | 1.55倍 | 32.2秒 |
| 100% | 1.8倍 | 1.80倍 | 27.8秒 |
| 50% | 10倍 | 1.82倍 | 27.5秒 |

つまり「ある画像処理が1.8倍」と「アプリが1.8倍」は異なる。
全体1.8倍には全時間の44.4%以上を削減する必要がある。未改善部分だけで55.6%以上なら達成できない。
Rustなら常にPillowより速い、または最大値が1.8倍という根拠は確認できていない。

PillowのWebPは既にlibwebpを利用している。同じコーデック・画質・methodなら、呼出言語の変更だけで圧縮の計算量は大きく減らない。
一方、コーデック、SIMD、コピー回数、探索アルゴリズムを改善すれば効果はあり得る。
WebPのmethodを下げる実験も現行Pythonで可能だが、画質・出力容量も比較する必要がある。
Rust `image` のWebPEncoderは現在losslessのみ。これを既存のlossy quality=90と比較して「Rustが速い」と評価してはいけない。

## 起動と容量

起動 = プロセス起動 + onefile展開 + import + DB読込 + UI初期化。
RustはPython importとonefile展開を避けられる設計にできるため改善は合理的だが、TauriにはWebView起動が加わる。
GUI操作可能までの時間を測らずに「何秒→何秒」とは言えない。
Pythonをonedir配布に変えるだけでも展開待ちを除けるため、比較対照に入れる。

容量は配布圧縮サイズ、展開後容量、追加ランタイム、実行時メモリを別に記録する。
Rust単独ならPython・NumPy・Tk分を削れるが、UI・TLS・コーデックの依存が加わる。現時点で具体的なMB値は未測定。
Tauriは既存WebView2を利用すれば小型化を期待できる一方、公式資料ではオフラインインストーラ同梱が約127MB増、固定Runtime同梱が約180MB増。
したがって「Web UIにしたら必ず小さい」は成立しない。Python処理をsidecarで残す構成も容量削減の主目的には合わない。
メモリ使用量もWebViewを含めて別途測定する。

## 方式の比較

| 方式 | 主な価値 | 制約・移行負担 | 評価 |
|---|---|---|---|
| Python/Tk維持 + 最適化・onedir | 小さい変更で起動改善を試せる | 大幅な依存削減は難しい | 最初の比較対象 |
| Python + Rust一部拡張 | 遅い工程だけ置換できる | Python配布は残り、二言語になる | 実測でホットスポットが見つかった時 |
| Rust + ネイティブUI | ランタイム削減、ローカル機能を維持 | GUI・更新・例外処理も移植 | 小型化優先なら候補 |
| Rust + Tauri Web UI | ローカル処理と画面刷新を両立 | WebView依存、RustとWeb双方の保守 | UI刷新込みの第一候補 |
| ローカルサーバー + ブラウザーUI | 現行処理を再利用しやすい | 起動・終了管理、localhostの認証/Origin検証、ブラウザー起動 | 段階移行には可能 |
| ブラウザー + Rust/WASM | アプリ配布不要、端末内処理も可能 | 保存権限・API互換性、公式DBのCORS、WASMコーデック、メモリ | 別製品としての需要がある場合 |
| サーバーで画像処理するWeb版 | 利用端末の負荷を減らせる | 画像アップロード、運用費、現行のローカル完結方針の変更 | 現用途では優先度低 |

Tauriなら画面からパスと設定をRustへ渡し、画像処理・保存・公式DB取得はRustで行う。
画像全体を毎回Base64化してUIと往復させず、必要なサムネイルと進捗だけを返す。
Web UI自体は高速化手段ではないが、要確認カードの比較、結果の絞り込み、プレビューを充実させる価値がある。
ブラウザーのshowDirectoryPickerは対応が限定され、権限操作も必要。公式DBのCORS許可は今回未確認で、ブラウザーからの直接更新を前提にできない。

## 移行判断の手順と完了条件

1. 実スクショを通常確定・探索・非カード・重複に分類し、FullHD/WQHD/4K、PNG/JPEG/WebP、出力3形式で現行版を計測。
2. Python onefile/onedir、Rust CLI試作を同じ画像・同じ保存設定で比較。1 workerと同数workerの両方、中央値/p95、全体経過時間を記録。
3. pHash、グレースケール、Lanczos、DCT精度、中央値比較、丸め・座標の互換性を検証。既存ハッシュDBをそのまま使えることが前提。
4. 特殊5カードの中央ハッシュ、枠違いカード、同順位、言語判別、重複、名前、キャンセル、保存失敗、データ更新・破損耐性を回帰確認。
5. `tools/regress.py` と既存baselineを用い、誤確定を増やさないこと、既存の確定例を退行させないことを確認。JSONのbaselineだけでは再実行できず、元画像が必要。
6. Rustコアが有望ならTauri画面を試作し、コールド/ウォーム起動を分離して操作可能まで測定。配布容量とWebViewを含むメモリも比較。

採用条件の提案（予測ではない）: 精度・機能互換を必須とし、速度目的なら実画像全体で1.5倍以上などの基準を事前に設定。
UI刷新・小型化が主目的なら速度倍率が小さくても採用理由になり得る。
現段階ではRust版をビルドしていない。PATH上にcargo/rustcがなく、実スクショ・配布exeもリポジトリにないため、Rustとの直接比較、起動と配布容量の実測は未実施。

## 試作環境と作業の引き継ぎ

現行版とは別の開発ディレクトリを用意し、Git worktreeと専用ブランチ（例: `codex/rust-prototype`）で試作する方針を推奨する。
Rust CLIで互換性と速度を確かめてから、TauriのWeb UIを試す。現行Python版は比較基準として残す。
設定・追加ハッシュ・出力先も分離し、試作版が現行のユーザーデータを書き換えないようにする。
worktreeは同じPC内の作業分離に使う。別PCではリポジトリをcloneし、そのPC上で必要なブランチ・worktreeを作る。

現在のPCはCドライブ容量への懸念があるため、空き容量とメモリに余裕のあるメイン機での開発を推奨する。
空き容量そのものは未計測。Rustのツールチェーン、Windowsビルドツール、依存、中間生成物、Web側の開発環境には配布exe以上の容量が必要になる。
メイン機で実装・ビルド・比較を行い、現在のPCは試作exeの起動・操作感を確認する環境として使える。
速度比較は必ず同一PCでPython版とRust版を測り、ハードウェア差を移行効果に含めない。

調査資料・計測スクリプト・参考結果はリポジトリに保存する。
試作コードはローカルの専用ブランチで進められ、公開リポジトリにpushすれば試作ブランチも公開される。
