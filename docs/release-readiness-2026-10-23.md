# リリース品質確認・版番号・名称の提案

確認日: 2026-10-23（日本時間）。対象は `claude/tauri-ui` の `a306bc7a1c8f3e30ce616ec213b53f4651e54703`。比較対象は `main` の `ce949e8`（Python版 1.4.1）。

## 判断

**`v2.0.0-beta.1` をプレリリースとして公開し、正式版 `v2.0.0` はまだ出さない。** 初回レビューで見つかったP1・P2の5件はコードとテストで解消し、実アプリでも確認した（下記）。データ移行も実装した。正式版の前には、新規PCでの起動確認、実際の旧版データでの移行確認、betaの利用者の報告への対応が残る。

確認は2段階で行った。最初のレビュー（`a306bc7`）は静的レビュー、ビルド、CLIの実画像処理が中心だった。その後の修正では、リリースexeを隔離したユーザーデータ（`APPDATA` を一時フォルダへ向けたもの）で実際に起動し、WebView2のリモートデバッグ経由で画面を操作して確認した。ウィンドウを閉じる操作は、ウィンドウに閉じる要求を送って確認した。新規PCでの起動・インストール、WebView2未導入の環境は未確認。「ビルドできる」ことを「製品として問題なく使える」ことと同一視しない。

## 解消した問題

### P1: 登録後の清掃が別の入力から保存した画像も削除した — 解消

各結果が実際に作ったファイルを `saved_paths` として保持し、`remove_review_copy` はその一覧のうち `review/`・`not_card/` 内の webp/png だけを消す。同じ名前の別形式は触れない。1つでも対象外のパスがあれば何も消さない。both形式では同じ処理が作った2ファイルだけが対象になる。

- テスト: 同名・別形式の別画像が残ること、both形式の2ファイルだけが消えること、すでに無いファイルを許容すること（`gui/src-tauri/src/lib.rs`）。結果の `saved_paths` が単一形式・both形式で正しいこと（`mdript-cli`）。
- 実アプリ: `not_card/shot.webp`（入力A）と `not_card/shot.png`（別フォルダの同名入力B）を作り、Bを登録して確定させた。Bのコピーだけが消え、AのWebPは残った。

### P1: 処理中に閉じると保存完了を待たなかった — 解消

終了時に画面が `shutdown` を呼ぶ。バックエンドは新しい処理の開始を止め、実行中の処理へ中止を伝え、処理が終わるまで待つ。処理が終わる印はpanicでも外れる。対象は画像処理、データ更新、登録時の照合データ追加、登録後の再処理。画像処理は、始まった画像の書き込みと `log.csv` の記録を終えてから戻る。

- テスト: 終了待ちが処理の完了まで戻らないこと、処理がpanicしても解除されること、終了後は新しい処理を始めないこと。途中で中止した処理が、空の予約ファイルを残さず、保存した画像と `log.csv` の行数が一致すること（webp・both）。
- 実アプリ（256枚、重複スキップなし）: 処理開始の約0.7秒後に閉じる要求を送った。webpは1.0秒、bothは1.7秒で終了し、保存ファイルは空でなく、`log.csv` の行数と一致した（webp 52件／52行、both 56ファイル／28行）。カード名の取得は、2.5秒後の閉じる要求で3.4秒後に終了し、`card_names.json` と一時ファイルは残らなかった。

### P1: 新アプリのタグでも旧Pythonアプリが配布された — 解消

`.github/workflows/build.yml` を新アプリ用に置き換え、`rust-prototype.yml` を統合した。PyInstallerによる旧版のビルド・リリース添付は残していない。

- Vueの型検査と本番ビルド、RustコアとTauri側のtest・clippy・fmt。
- リリースexeのビルドと、`tools/package_release.py` による配布物（zip: exe・LICENSE・第三者ライセンス・利用案内、SHA256SUMS.txt）の作成。公開はせず、artifactとして保存する。
- `tools/check_release_version.py`: `tauri.conf.json`・Cargo・npm・各ロックファイルの版が一致すること、タグ（`v*`）が製品版と一致し、v2以降であることを検査する。
- 利用案内にWebView2 Runtimeの前提と、exeに署名がないことを明記した。旧Pythonテストは基準実装の回帰テストとして残し、配布はしない。
- ローカルで配布物の生成まで実行して確認した。**GitHub Actions上の実行は未確認**（pushしていない）。製品版は `2.0.0-beta.1` に揃えた。タグ `v2.0.0-beta.1` だけが通り、`v2.0.0` や `v1.x` は止まる。
- 第三者ライセンスは `tools/third_party_notices.py` が、Windows向けにリンクするRustクレートと本番のnpm依存の表記を一覧にし、同梱のライセンス文を載せる。クレートに文書が同梱されていない `alloc-stdlib`・`selectors`（MPL-2.0）・`webview2-com` 系は、上流のリポジトリ（selectorsはMozillaのMPL-2.0）から取った文を `rust/third-party/supplement/` に置いて補う。ライセンス文がない依存が1つでもあれば、配布物の生成を止める。

### P2: CSVを書けなくても成功として扱った — 解消

`write_csv` の失敗を `csv_error`（対象パスとOSのメッセージ）として終了結果に入れる。画像の件数・エラー数には混ぜない。画面は状態欄と警告に表示し、CLIは標準エラーにも警告を出す（終了コードは画像の失敗件数だけで決まる）。登録後の再処理で失敗した場合も警告する。

- テスト: `log.csv` がディレクトリのとき、Windowsで他のプロセスが共有なしで開いているときに、画像は保存され、エラー数0、`csv_error` にパスが入ること。
- 実アプリ: `log.csv` をディレクトリにして処理し、「確定 1 / エラー 0」のまま「ログを保存できませんでした」を表示した。

### P2: 確認・登録後の再処理が元の設定を引き継がなかった — 解消

処理を始めたときの出力先・形式・解像度・言語などを結果ごとに保持し、再処理と古いコピーの清掃にはそれを使う。

- 実アプリ: 出力先Aで処理したあとに、画面の出力先を別の場所に、形式をbothに変えて登録した。再処理はAに元の形式（png）で保存し、新しい出力先には何も作らなかった。
- 画面側のこの判断にはユニットテストがない（GUIにテスト基盤がないため）。実アプリの操作で確認している。

### ユーザーデータの保存先と移行 — 実装済み（beta向け）

正式版の保存先を `%APPDATA%\mdript-v2` にした。旧版の `%APPDATA%\mdript` を、初回起動時に読み取り専用の移行元として扱う（`gui/src-tauri/src/migrate.rs`）。CLIの保護（旧版のフォルダへ書き込む処理の拒否）は変えていない。`mdript-v2` は旧版のフォルダの外にあるため、保護はそのまま通る。

- コピーするのは設定・カード名・登録した照合データの3ファイル。旧版のフォルダは変更も削除もしないので、旧版へはそのまま戻れる。
- コピー前に原本を `mdript-v2\legacy-backup\` に控える。書き込みは一時ファイル経由で、途中で止まっても半端なファイルを残さない。
- JSONとして読めない、または形の違うファイルは取り込まず、画面に知らせる（原本は `legacy-backup` に残る）。設定は既知の項目だけを取り込む。
- 新アプリ側にすでにあるファイルは上書きしない。完了すると `migration.json` を残し、以後は何もしない。途中で止まったときは印がないので、次の起動で残りだけをやり直す。
- テスト（`migrate.rs`）: 旧版が変わらないこと、破損ファイルの控えと不取り込み、再実行と上書きなし、中断後の再開、旧データがない場合。実アプリで、隔離したデータに旧版のファイル（1つは破損）を置いて起動し、コピー・控え・旧フォルダ不変・再起動時の不再取り込みを確認した。
- 未確認: 実際の旧版（Python）が作った本物のデータでの取り込み。旧版が追加で保存するファイルがあれば、取り込まれない。

## 版番号とリポジトリ

**推奨は、同じ `yugioh-hack/mdript` で v2。** 版番号とリポジトリの分割は独立した判断である。

| 方針 | 評価 |
| --- | --- |
| 同じリポジトリで v2.0.0 | 推奨。利用目的・カードデータ・履歴・Issue・既存の入手先を継続し、UI刷新と移行の節目を伝えられる |
| 同じリポジトリで v1.5.0 | ユーザーデータ・CLI・配布手順の互換性を保つ追加更新なら可能。現在はCLI引数やデータ保存先も異なるため、変更を小さく見せやすい |
| 新しいリポジトリで v2.0.0 | 独立製品として旧版と長期に並行運用する場合に検討。Rust化やUI刷新だけでは分割の利点が小さく、入手先・Issue・文書が分散する |

[SemVer](https://semver.org/lang/ja/)は非互換の公開API変更でメジャー、互換性のある機能追加でマイナーとする。Rust化という内部変更だけでv2が必須になるわけではない。今回はCLI変更・データ移行・大幅な操作変更をまとめる製品判断としてv2を推奨する。

具体的には、旧Python版をタグ `v1.4.1` で残し、必要なら現行mainから `maintenance/1.x` を作る。新UIの修正と配布CIを完了してからmainへ統合する。まず `v2.0.0-beta.1` をGitHubのプレリリースとして公開し、旧版からの移行確認後に `v2.0.0` を公開する。この文書ではブランチ作成・統合・タグ付け・公開は実行していない。

## 名称

表示名は **開闢（かいびゃく）― マスターデュエル カード画像ツール** に決まった。2.0.0 の名前「開闢」を、画面タイトル・ダイアログ・READMEに入れた。説明の部分（マスターデュエル カード画像ツール）は、切り抜きだけでなく確認・検索・照合データ登録も扱う内容を日本語で伝える。

- 切り抜き用途を最優先にするなら「マスターデュエル カード切り抜きツール」。
- 英語名も付けるなら「Master Duel Card Image Tool」。
- `mdript` は開発コード、リポジトリ名、exe名として継続してよい。製品名と内部識別子を揃える必要はない。表示名を変えるためだけに設定フォルダやTauriの識別子を変えず、既存利用者がデータを引き継げる設計を優先する。

名称候補は商標・名称重複の調査済みという意味ではない。
